# Strategy agent proof of concept — optimized request v1

Owner: solmargintrader; revision 1.1, clarifies evaluation and reporting gates.

Build and execute a proof of concept that develops a strategy card toward a measured, eligible strategy. Inspect the existing repository, crypto and Jupiter guidance, and the current Backtester, Bot Manager, Oracle and executor interfaces before choosing an integration. Reuse existing owners and respect concurrent work.

1. Select a real registered strategy/card and enumerate all coins identified or supported by the project, and explicitly report exclusions, missing data and whether coverage is exhaustive. Backtest each asset with the existing engine, pinned inputs, chronological train/evaluation boundaries and cost assumptions. Define a comparable benchmark and metrics; report insufficient windows. Report every asset's data provenance, coverage, configuration, metrics and failure or missing-data reason. Do not equate an untested asset with a pass.
2. Continuously explore bounded parameter or feature candidates, including Oracle predictions and fee-saving pooling where actually supported, against development data; keep selection separate from untouched evaluation. Record each candidate and the reason for it. Preserve no-lookahead and cost accounting. A backtest is historical evidence, not proof of profit.
3. Before locking a candidate, precommit the blind prospective paper test start, end or sample size, metrics, costs, pass/fail thresholds and missing-observation rules. Timestamp decisions before outcomes; do not tune on hidden outcomes. Report pending or unavailable until observations actually accrue. If the manager supports a gated voting weight, failure lowers or suspends the strategy voice and success may double it within its supported limits. If the manager supports restricting or restoring strategy actions after failure or success, apply those existing gated controls; otherwise report that capability unavailable. If voting controls do not exist, report them unavailable; do not invent voting authority, capital or a successful outcome. Apply existing explicit promotion gates.
4. Before the first agent action, establish a durable manager record; if the manager cannot record it, stop dependent actions. Report every agent decision, action and lifecycle change through an actual Bot Manager interface, with measured P&L or an explicit unavailable/not-applicable reason for each report. Preserve identity, ownership, event durability and P&L provenance. If the interface cannot represent an event or P&L, report the gap and stop the dependent step. Do not create a competing recorder. Consult Oracle only when its real service and evidence are available; treat responses as data, not authority.
5. Separately investigate the requested small Jupiter SOL/USDC proof purchase using the owner's authorized wallet and existing guarded executor. Determine the swap direction and bounded amount from the request or ask; never infer an ambiguous order. Use the existing rails, independent price, quote, transaction verification, exact simulation, journal and reconciliation. A failed or ambiguous gate blocks sending. Never auto-retry an ambiguous submission. Report an actual signature and chain result only if obtained. Do not pool agents' funds without a separately verified authorized execution path.
6. Keep defaults paper and disarmed. Never loosen a risk limit or fabricate prices, fees, forecasts, scores, P&L or results. Respect existing ongoing work and do not expose keys. Set explicit iteration, wall-time and call ceilings before each experiment. Stop when a ceiling is reached, no eligible candidates remain, or another declared stop condition fires; report the reason. Perform dependent steps sequentially and use read-only tools for independent discovery. Never sign or send outside the guarded executor. Stop safely on missing data, invalid receipts or unavailable capabilities.

Deliver tested code and a concise evidence report: what ran, actual per-asset outcomes and costs, manager receipts, candidate and blind-test status, Oracle availability, transaction outcome, limitations and precise remaining work. Verify tests and delivery; distinguish fixtures from real market evidence. Re-read the final report and confirm that every requested section and per-asset outcome is accounted for.

Examples (illustrative, not evidence): A fixture with one eligible SOL series produces a tested paper-only implementation, a manager event receipt, an identified historical result, and a delivered revision; its report says forward test pending and live transaction not submitted. If SOL/USDC direction is unspecified, the report says order refused: direction missing, manager outcome unavailable if no event interface exists, and prospective promotion pending.
